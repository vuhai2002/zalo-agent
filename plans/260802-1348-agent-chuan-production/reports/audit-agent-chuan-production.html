Agent của zalo-agent đã đúng chuẩn production chưa?

Đối chiếu code thật với định nghĩa agent của Anthropic, OpenAI, 12-Factor Agents, và với source hermes-agent. Kết luận ngắn: vòng lặp agent đúng chuẩn, phần chịu lỗi trên trung bình rõ rệt, còn thiếu đo lường và một chỗ sai định nghĩa.

Ngày 02/08/2026 Nhánh main @ c467731 Đọc src/agent/ + src/conversation/ + src/zalo/ Tham chiếu hermes-agent/agent/ (114k dòng)

Đúng định nghĩa agent chưa?

Rồi, về bản chất vòng lặp

Theo Anthropic, agent là hệ mà LLM tự điều khiển tiến trình và tool của chính nó (khác workflow: đi theo đường code định sẵn). agent-loop.ts đúng vậy - không có đường code nào ép thứ tự tool.

Đã production-grade chưa?

Một nửa

Chịu lỗi + chống injection: trên mức trung bình rõ rệt, có những nhánh chỉ xuất hiện sau khi đã đau thật. Đo lường + chống lãng phí: chưa có eval, chưa có loop guardrail, đếm ngữ cảnh nhầm đơn vị.

Sai định nghĩa ở đâu?

Đúng 1 chỗ

Trục agent không có quyền gì với tool. disabled_tools chỉ nằm ở bảng accounts, nên có N agent mà chỉ điều khiển được một trục. Mục 8/A đã được đính chính ngày 02/08 - đọc phần đó trước khi làm.

01

Định nghĩa: agent khác workflow ở chỗ nào

Anthropic tách rạch ròi hai thứ mà người ta hay gọi chung là "agent". Phân biệt này quyết định mình đang xây cái gì.

Khái niệmĐịnh nghĩa
Workflow LLM + tool được điều phối qua đường code định sẵn. Dễ đoán, hợp việc đã rõ các bước.
Agent LLM tự điều khiển tiến trình và cách dùng tool của chính nó, giữ quyền quyết định làm thế nào để xong việc.

Vòng lặp agent theo Anthropic: nhận lệnh -> lập kế hoạch -> gọi tool -> nhận kết quả từ môi trường -> tự đánh giá tiến độ -> lặp tới khi xong hoặc chạm điều kiện dừng.

OpenAI định nghĩa gọn hơn: agent là hệ tự hoàn thành một quy trình nhiều bước thay người dùng, có ra quyết định, gọi tool, và phục hồi được khi hỏng. Ba thành phần bắt buộc:

Thành phầnVai tròzalo-agent
ModelBộ não suy luậnCó đặt riêng được theo agent
ToolsTay chân: thu thập ngữ cảnh hoặc tác động ra ngoàiCó, nhưng gắn nhầm chỗ
InstructionsLuật hành xử và ranh giớiCó phân lớp rõ ràng
✓ Kết luận: agent-loop.ts là agent thật, không phải workflow. generateText + stopWhen: stepCountIs(n) + tools - model tự chọn tool nào, chạy mấy bước, khi nào dừng.
02

Context engineering - phần làm tốt bất ngờ

Anthropic gọi đây là kỷ luật "chọn tập token tối ưu tại mỗi lần suy luận", và nêu 3 kỹ thuật cho tác vụ dài hơi. Mình đã có 2 trong 3.

Kỹ thuật AnthropicTrạng tháiỞ đâu trong code
Compaction
gộp hội thoại cũ thành tóm tắt		 Có thread-summarizer.ts - rolling summary, fire-and-forget sau khi đã trả lời, lỗi summary không phá lượt chat
Structured note-taking
agent tự ghi chú ra ngoài		 Có save_memory + bảng memories, kèm quy tắc privacy bất đối xứng (fact học ở DM không bao giờ chảy ra group)
Sub-agent
agent con, ngữ cảnh sạch		 Chưa -

Mấy điểm đúng chuẩn mà nhiều bản triển khai bỏ qua

  • System prompt chia khối rõ ràng (persona-prompt.ts): persona nền, ngày, khả năng, luật từng tool, persona riêng, tóm tắt, trí nhớ, bối cảnh. Đúng khuyến nghị "tổ chức theo section".
  • Chỉ đưa NGÀY, không đưa GIỜ vào prompt - giờ đổi mỗi phút sẽ vỡ prompt cache mỗi phút. Chi tiết này ít người nghĩ tới.
  • Mục "khả năng" sinh từ ĐÚNG bộ lọc dựng schema - listAvailableTools dùng chung cho cả buildAgentTools lẫn buildSystemPrompt. Chặn hẳn lớp bug "prompt hứa một tool mà model không hề nhận được".
  • Cắt output tool (WEB_FETCH_MAX_CHARS=15000) - đúng nguyên tắc token efficiency.
  • Tool bị tắt biến mất khỏi schema, không phải "có nhưng trả lỗi" - vừa tiết kiệm token mô tả vừa chặn injection dụ gọi.

Chịu lỗi - chỗ trên mức trung bình

Mấy nhánh này hiếm thấy ở bản tự viết. Chúng thường chỉ xuất hiện sau khi đã bị đau thật ở production.

Cơ chếVì sao cần
Lượt chốt khi hết step
runWrapUp		 Chạm trần step thì gọi lại model không cấp tool, ép nó viết câu trả lời từ dữ liệu đã thu được. Không có nhánh này thì người dùng nhận đúng câu tường thuật nội bộ ("Đủ 2 nguồn - giờ đối chiếu") làm câu trả lời.
Nhận diện completion rỗng
isEmptyRouterCompletion		 Router trả HTTP 200 + 0 token + 0 tool call. SDK coi là thành công nên maxRetries không cứu được.
Fallback khi provider từ chối ảnh Bắt 4xx, ghi nhớ model mù, dựng lại input không pixel, thử lại 1 lần.
Trace sống sót qua throw Mảng trace do caller sở hữu, agent-loop chỉ push. Lượt chạy tốt 5 step rồi step 6 gặp 500 vẫn còn đủ manh mối.
Log cả tool-error Tool ném exception không bao giờ lọt vào toolResults (đo thật với ai@7.0.37). Không log riêng thì lỗi tool không để lại dấu vết nào.
Sanitizing fetch Cắt đuôi data: [DONE] mà 9Router dính vào body JSON non-streaming - không cắt thì cả lượt chết dù token đã tốn.

Hermes có gì mà zalo-agent chưa có

Đọc hermes-agent/agent/ (114k dòng Python). Lọc ra thứ đáng học, bỏ thứ chỉ hợp agent coding.

tool_guardrails.py (479 dòng) - đáng học nhất

Chống vòng lặp tool ở mức chữ ký lệnh gọi:

  • ToolCallSignature = tên tool + hash JSON args đã chuẩn hóa (sort key, compact) - nhận diện được "gọi y hệt lần trước".
  • Ba bộ đếm riêng:
    • exact_failure - đúng tool + đúng args + lại lỗi. Cảnh báo sau 2, chặn sau 5.
    • same_tool_failure - cùng tool lỗi với args khác nhau. Cảnh báo 3, dừng 8.
    • idempotent_no_progress - tool chỉ đọc trả về cùng kết quả lặp lại. Cảnh báo 2, chặn 5.
  • Chia sẵn IDEMPOTENT_TOOL_NAMES vs MUTATING_TOOL_NAMES - chỉ tool đọc mới áp luật no-progress được (ghi 2 lần khác nhau là hợp lệ).
  • Bộ điều khiển thuần, không side effect: before_call/after_call trả về quyết định (allow/warn/block/halt), runtime tự quyết biến nó thành warning, tool result giả, hay dừng lượt.
  • Mặc định warnings_enabled=True, hard_stop_enabled=False - phiên tương tác chỉ bị nhắc nhẹ, chặn cứng phải bật tường minh.
⚠ zalo-agent hiện chỉ có stepCountIs(8). Model gọi web_fetch cùng một URL lỗi 5 lần liên tiếp thì đốt 5/8 step, không ai chặn, người dùng ngồi đợi.

context_engine.py (489 dòng)

Context engine cắm rời được, vòng đời rõ: on_session_start -> update_from_response(usage) -> should_compress() -> compress() -> on_session_end.

Điểm mấu chốt: quyết định nén dựa trên usage token THẬT trả về từ API, không phải đếm số tin. zalo-agent đang đếm 20 tin (HISTORY_CONTEXT_LIMIT), mà một tin Zalo có thể dài tùy ý.

Thêm sanitize_memory_context(): redact + cắt đầu-đuôi (giữ 4000 ký tự đầu, 1500 cuối) khi ngữ cảnh memory vượt 6000 ký tự - cắt giữa chứ không cắt đuôi, vì phần cuối thường là thứ mới nhất.

Còn lại

  • iteration_budget.py (62 dòng) - bộ đếm lượt lặp có khóa, có refund(). Mỗi agent con có ngân sách độc lập.
  • error_classifier.py (1699 dòng) - phân loại lỗi provider để quyết định retry / đổi model / bỏ cuộc. zalo-agent retry mù maxRetries: 2 + 2 nhánh đặc thù: hết quota, context tràn, và mạng chập đang bị xử lý y như nhau.
  • memory_manager.py - chỉ cho phép MỘT memory provider ngoài tại một thời điểm, chặn phình schema tool và backend trí nhớ đá nhau. Kèm normalize_tool_schema() xử lý ca schema bị bọc 2 lần khiến DeepSeek trả 400 và hỏng cả toolset.
ℹ Cái Hermes có mà mình KHÔNG nên lấy: auxiliary_client.py 8255 dòng, conversation_loop.py 6645 dòng, MoA loop, LSP, browser provider, credential pool. Hermes là agent coding đa nền tảng - độ phức tạp đó không mang lại gì cho bot Zalo cá nhân. Giữ nguyên quyết định "tự viết agent loop, không dùng framework".

Chênh lệch với hình dạng agent hiện đại

Ảnh ChatGPT Agent Builder cho thấy một Agent hiện đại sở hữu toàn bộ cấu hình của nó.

zalo-agent hiện tại:

Account (Zalo credential)              Agent (bảng `agents`)
 |                                      |
 +-- allowlist                          +-- persona

Đây là chênh lệch cấu trúc lớn nhất. Xác nhận bằng code:

  • disabled_tools là cột của bảng accounts - database.ts:249
  • agent_id cũng ở accounts - database.ts:74
  • agent-routes.ts không hề có trường tools

Hệ quả thật

  • Đổi agent của một account -> toolset không đổi theo.
  • Hai account dùng chung một agent -> hai toolset khác nhau.
  • Không dựng được "Trợ lý bán hàng" (chỉ web_search + create_excel_file) và "Trợ lý kỹ thuật" (đủ tool) rồi gắn/tháo trên cùng một nick.
⚠ Theo cả OpenAI lẫn Anthropic, Agent = instructions + tools + model. Tool là thuộc tính của agent, không phải của kênh. Thiếu thêm: Files/knowledge base cho agent (không có RAG), và memory gắn theo agent (memory hiện gắn theo account + subject).

09

Chốt lại

Đã đúng chuẩn agent chưa? Rồi, về bản chất vòng lặp. Đây là agent thật theo đúng định nghĩa Anthropic: model tự điều khiển tiến trình và tool của nó, có điều kiện dừng, có phản hồi từ môi trường.

Đã production chưa? Phần chịu lỗi và chống injection thì trên mức trung bình rõ rệt - lượt chốt không cấp tool, nhận diện completion rỗng, fallback ảnh, trace sống qua throw, khử tên thẻ trong nội dung web. Mấy thứ này thường chỉ xuất hiện sau khi đã bị đau thật ở production.

Ba việc còn thiếu, theo đúng thứ tự

Eval harness (C)Không có thì mọi cải tiến sau này đều là đoán. Đây là nền cho hai việc còn lại.
Loop guardrail (B)Lỗ hổng đốt tài nguyên duy nhất còn hở trong vòng lặp.
Ngân sách token thật (D)Hiện đang đếm nhầm đơn vị. usage đã có sẵn, chỉ là chưa dùng.
⚠ Sai định nghĩa ở đâu? Đúng một chỗ: agent không sở hữu tool của chính nó (A). Nếu mục tiêu là "đúng cấu trúc chuẩn của một agent" thì sửa cái này trước.

  3. Human-in-the-loop (F) muốn hình dạng nào - bot hỏi lại trong chat, hay nút duyệt trên dashboard?
